# Project Stephanus
## 本地数据筛选、精简与整合计划 v0.3（建议稿）

日期：2026-11-10。状态：规划完成，数据库迁移与归档尚未执行。

> 历史建议稿，已由 [compact-v1 实施方案](compact-runtime.md) 替代。新方案实际删除冗余原料，不采用本稿的本地归档安排。

本稿结合本次提供的《本地数据筛选、精简与整合计划 v0.2》、上一阶段已确认的《资源收集与查询工具 MVP 实施计划》，以及当前代码与本地数据记录修订。上一阶段的实现情况见 [IMPLEMENTATION.md](../IMPLEMENTATION.md)，项目约定以 [agent.md](../agent.md) 为准。

### 一、本阶段的目标与边界

将已有查询 MVP 整理为可独立离线运行、重复信息较少、便于未来 Agent 调用的姓名与词典工具。继续采用 Python、SQLite、现有 Service、CLI 和七个只读 MCP 工具，以及原生 JSON、SQLite、verba、python-romkan 的混合接入方式。

本轮主要完成源记录共享、必要字段筛选、检索整合和运行资源打包。名称拉丁化与创作 skill 继续后置；未来由 Agent 选择转换路线、联想语义或直接创作，不要求本轮数据库预先建成全部跨语言转换关系。

遵守 MVP、尽量复用、禁止哈希校验及重复验收的约定。统一模型只落实当前查询实际需要的部分；保留多种参考结果，不引入语言学准确率、候选综合评分或复杂证据审计系统。

这次改造的重点是保存同样有用的知识时减少重复，而不是建立完整的姓名学实体系统。

`dbstat` 的统计口径参见 [SQLite 官方文档](https://www.sqlite.org/dbstat.html)。本次没有测量逐来源可节省字节或查询延迟，不据此给出压缩比例和提速承诺。

### 四、数据保留与筛选规则

Core、Lexicon、Extended、Archive 表示用途和安装策略，不要求各自对应一个数据库，也不要求给整个来源只分配一个等级。

| 来源或内容 | 默认归属与接入方式 | 本轮处理 |
|---|---|---|
| JMnedict | Core，统一索引 | 保留现有姓名范围、写法、读音、类别和上游 ID；同一原记录的多写法共享内容 |
| jinmei-dict | Core，保留原生 JSON 适配器 | 保留姓名数据和必要说明；同音候选通过读音查询得到 |
| Japanese Personal Name Dataset | Core，原生 SQLite | 保留实际查询文件及现有 ID；无需再复制成一整套统一实体表 |
| Medieval 欧洲姓名 CSV | Core，统一索引 | 保留规范名、历史形式、地区、年代、格及文献字段；und 继续有效 |
| Onomaverse 姓名及关系 | Core，统一索引 | 保留现有关系类型与两端记录，包括被默认保留的转写端点 |
| Onomaverse 已索引本地化写法 | 默认保留于运行库 | 先共享原记录和压缩字段；未来明确选择语言子集时再输出覆盖变化清单 |
| Onomaverse 频率、节日、流行度等 | Extended | 默认运行包可不携带，但仍可选用原数据或现有 supplements 接入 |
| JMdict、KANJIDIC2 | Lexicon，统一索引 | 保留现有词条、读音、适用范围和词义；字义用于姓名意象参考 |
| Kaikki 日语、拉丁语 | 按记录进入 Core 或 Lexicon | 优先筛字段，保留词条、义项、词源、读音、词形及已有关系 |
| CLTK 专名表 | Core 的辅助词表 | 保留 proper_name 和原写法；源文件缺乏人名、地名标签时不强行细分 |
| verba 及其实际读取的数据 | Lexicon，继续封装原程序 | 保留 verba.py、相关 source 文件及署名说明；暂不重建词典引擎 |
| python-romkan | Core 的运行工具 | 保留源码模块及许可说明，继续沿用当前导入方式 |
| 原始 XML、完整 JSON/JSONL、压缩包、参考工程与文献 | Archive | 按重建用途归档，保留版本、来源和重建方法 |

#### 4.1 Kaikki 与日语词典的字段策略

运行库优先保留：原写法、词条语言、词性、姓名类别、读音及体系、义项解释、必要标签、词源说明、词形及其所指词目、变体和相关词、可用的上游定位信息。

JMdict 的读音适用写法、义项适用写法或读音等限制必须随投影保留。Kaikki 的词形条目即使缺少独立词源说明，也可能是拉丁语检索的入口，不能仅因此删除。普通词汇中的植物、颜色、地形等继续作为创作材料保留，不先建设人工主题白名单。

模板展开中间字段、重复展示文本及当前不使用的大型附加内容可留在归档。完整原始资料仍由归档保存，运行库保存筛选后的结构化记录。`get_entry` 应说明返回的是运行版保留的字段，并提供原始来源定位；相应工具说明需随迁移更新。

#### 4.2 配置与版本清单

复用 `resources.json` 保存资源地址、版本、取得状态和来源说明，增加必要的用途或归档状态字段即可。筛选规则单独放入一份小型 `data-policy.json`，记录保留字段、可选数据及默认覆盖范围，不再复制一套 source_versions 清单。

本机归档路径保存在忽略的本地映射文件中，公共资源清单记录逻辑位置和重建入口。数据已经归档与数据尚未取得应当区分，避免常规操作重新下载已有归档。

### 五、统一模型的最小实现

#### 5.1 本轮采用的结构

| 结构 | 本轮职责 |
|---|---|
| source_records（新增） | 每个源快照中的一条上游记录只保存一次；包含上游定位、共有解释、搜索文本和筛选后的结构化字段 |
| entries（改造） | 保存可返回给用户的具体写法及已有公开 ID，引用 source_records；姓名、词汇、汉字继续使用 kind 区分 |
| readings（复用） | 保存写法对应的原始读音、检索键和可用的体系标签；保留多读音及适用范围 |
| relations（复用） | 保存关系两端、原关系类型和来源；需要的原字段放入轻量扩展内容 |
| supplements、imports（复用） | 保留可选补充数据接入和导入记录；记录本轮使用的规则版本与数据快照 |
| FTS5（改造） | 索引 source_records 的搜索文本和共有解释，通过记录引用返回具体写法 |

数据库内部可使用整数键连接，公开结果继续返回现有字符串 ID。SourceRecord 在这里是上游记录的运行版投影；完整原始记录保存在归档，避免在每个写法下重复存放。

Name、Lexeme、WrittenForm 先由 kind、entries 和 source_records 表达；Sense 暂保留结构化义项数组；Attestation 暂保留已有文献字段；Concept 暂用词义、标签或 Agent 解释表达。未来出现独立检索这些实体的实际需求时再拆表。

#### 5.2 去重、关联与 ID

同一来源同一上游记录的不同写法共享 SourceRecord；不同来源的同字姓名保留各自来源记录，可并列展示或附上关联。

共同的规范化检索键只用于查找。原始文字、重音、历史拼写和原读音照常保存；不使用规范化键认定姓名实体相同。异体字、同音异字、不同读法分别保留，不生成同音组内两两连接的巨大关系网。

JMdict、JMnedict 优先用上游记录 ID 共享数据。没有上游 ID 时使用数据快照和原始行号定位；不生成哈希，不做跨来源全库模糊实体合并。

优先从旧数据库已有记录构建新库，保留公开 ID 与关系端点。特别是现有 Kaikki ID 来源于读取时的行号，从全语言文件切换到提取文件后直接重新编号会改变 ID；迁移时应沿用旧 ID。后续原始数据重建需要保存原行号映射，Onomaverse 的筛选也应在保留原序号的基础上进行。

Medieval 的规范名作为该来源自己的组织方式保留。与 Onomaverse 的跨库联结先采用已有明确对应；相同拼写可以作为联合检索线索。`variant`、`similar`、`cultural_equivalent` 和 `transliteration` 沿用原类型。

CLTK 当前只是候选专名词形表，已有上游 README 也说明存在处理残留；本轮保留辅助用途，不将它扩展成自动分类或词形清洗项目。

### 六、数据库、查询与原生依赖

#### 6.1 FTS 与普通索引

采用单个统一 SQLite 运行库作为首选方案。SourceRecord 层将同一原记录的多写法和共有解释集中保存，FTS 以该记录的整数键建立 external-content 索引，搜索命中后关联 entries。结果按公开 ID 去重后再分页。

external-content 仍需要倒排索引，也需要由构建代码确保正文与索引同步；不能只声明表就认为已有数据被索引。本轮采用离线构建、查询只读，在内容写入完毕后集中建立索引，复用 SQLite 原有机制。[SQLite FTS5 官方说明](https://www.sqlite.org/fts5.html#external_content_tables)

姓名写法和前缀、假名读音、关系端点继续使用普通索引；按来源、语言、类别保留实际需要的筛选索引。地区和年代本轮先保留原字段，不因未来可能查询就预建所有索引。保留当前词形和释义查询能力，不引入新的分词框架。

#### 6.2 统一排序与分页

当前 `Service.search_names` 直接拼接数据库与原生后端结果。新版本需要让适配器提供内部匹配顺序，在合并候选后使用相同顺序分页：精确写法或读音、前缀、释义，再按检索键、来源及公开 ID 稳定排列。

数据库与原生适配器需支持这一候选顺序及足够的候选范围，不能各自任意截断后只做表面排序。日语姓名原生 SQLite 的查询也需要确定的顺序。仍用简单匹配优先级，不引入综合评分。

跨来源同名结果保留来源差异；同一个公开 ID 的重复匹配只返回一次。共同读音和汉字释义可通过已有查询取得，暂不要求预建姓名到全部汉字、同音候选的关系边。

#### 6.3 真正需要保留的运行文件

当前 `native.py` 与 `paths.py` 直接读取这些位置：

- `vendor/jinmei-dict/jinmei/mei.json` 与 `sei.json`。
- `data/raw/japanese-personal-name-dataset/japanese_names.sqlite`。
- `vendor/verba/verba.py` 及其实际使用的 `source/` 数据；当前 source 目录只有少量预构建词典文件，先整体保留更省开发工作。
- `vendor/python-romkan/src/romkan/`。
- 运行根目录中的 `resources.json` 与 `targets.json`。

因此，不能把整个 vendor 或整个 data/raw 一起迁走。verba 的上游词典工程可归档，仍需保留 verba 自己读取的数据和必要许可、署名说明；无需改变其词典与词形分析实现。

jinmei 的线性查找如在实际使用中成为瓶颈，可增加小型反向索引；本轮先保留可用适配器，不为打包提前引入缓存服务或新引擎。

### 七、目录与可独立运行的数据包

优先保留现有源码布局，新增构建与打包脚本按需拆分，不把 adapters/database/services 目录迁移作为交付前提。

第一版精简运行包使用与当前路径兼容的结构：

```text
Stephanus-Runtime/
├── resources.json
├── targets.json
├── data/
│   ├── stephanus.sqlite
│   └── raw/japanese-personal-name-dataset/japanese_names.sqlite
└── vendor/
    ├── jinmei-dict/          # 需要的 JSON 与来源说明
    ├── verba/                # CLI、source 数据与来源说明
    └── python-romkan/        # 源码模块与许可
```

项目代码和 Python 环境继续由源码安装提供；打包时附上已有安装方法。现有 `STEPHANUS_HOME` 指向的是资源根目录，运行包根目录中必须带有上述清单与目标配置；直接指向一个只含 SQLite 的目录不能满足当前代码。

如果实施中改用 `data/runtime/`，需要同时更新数据库、原生后端、清单、目标注册表及管理命令的路径解析。默认采用兼容结构，减少这一步改造。

原始压缩包、全量 JSONL、未参与运行的参考源码及文献放在独立的 `Stephanus-Archive/`。运行包不引用归档路径；重建命令可以按本地映射读取归档。重建采用原版本快照，未来新增语言时再选择对应数据集，本轮不重新下载或切换数据版本。

### 八、执行顺序与各步产物

| 工作包 | 依赖与内容 | 产物及终点 |
|---|---|---|
| A：补充画像 | 复用已有体积与导入记录，补充数据库对象空间和运行代码依赖 | 本轮空间报告已完成；后续所需逐源字段字节统计合并到 C 的首次消费，不再全盘重扫 |
| B：固定筛选与保留规则 | 依据 A，列出运行文件、保留字段、可选数据及 ID 保留方式 | data-policy.json 与运行文件清单；原始资料继续保留 |
| C：构建精简库 | 复用 importers、Writer、原有数据和旧 ID，新增 SourceRecord 引用并集中建索引 | 独立目录中的新库及构建过程自动记录的数量、字段和版本；不覆盖旧库 |
| D：接入查询与精简后端包 | 在 C 基础上接回 Service，处理详情、排序和分页；收集真正运行依赖 | CLI 与七个 MCP 工具的候选运行版、兼容路径的后端子集 |
| E：形成候选运行包 | 按清单包含原生 SQLite、JSON、词典程序、配置和说明 | 可与原始资料分离的运行包；此时原文件仍在原位 |
| F：一次集中验收 | 使用 E 的运行包，关闭服务后配置独立资源根；让本次新进程无法访问原资源根或归档 | 本阶段唯一的功能与打包验收报告，以及同一过程中的最终体积统计 |
| G：切换与归档 | 按 F 的实际结果决定是否切换；成功时关闭连接后迁移已列明的构建资料 | 本地归档映射、使用与重建说明；不再追加一轮“迁移后验收” |

C 的构建计数是首次处理数据时产生的日志，不另建循环复核流程。旧库保留到新阶段验收结果明确；不同时额外复制整套原始数据作为快照。构建期额外空间按新库、索引临时文件和运行包计算，不能用最终 1–2 GiB 的期望值代表峰值需求。

`resources.json` 的取得状态、归档映射和 fetch/import 行为应随归档动作更新，避免后续管理命令把大文件重新拉回运行目录。`STORAGE.md` 与 `IMPLEMENTATION.md` 作为旧阶段快照保留，新的实施和空间结果另存文件。

### 九、唯一一次验收的内容

本阶段交付的是新数据库与运行包，验收只针对这一新产物进行一次。不得重跑旧 `scripts/accept_once.py`、覆盖 `data/acceptance.json`，也不把旧记录描述为全部通过。

复用旧验收代码中的场景与 MCP 客户端写法，形成阶段专用的一次运行入口，保存至新报告路径，例如 `data/reports/runtime-integration-acceptance.json`。报告存在时不重复执行。

| 场景 | 本次一次性观察的结果 |
|---|---|
| 日本姓名及同音异字 | 保留现有写法与多读音；同音候选保留不同 ID 和来源 |
| 日语词汇与汉字 | JMdict、KANJIDIC2 及 Kaikki 可查询，必要字段可通过详情取得 |
| 拉丁语词典及分析 | verba 英拉查询、Kaikki 词条及词形、拉丁语分析可用 |
| 欧洲姓名及关系 | 现有 ID 可获取详情，历史变体及 Onomaverse 关系端点可达 |
| 罗马字转换 | python-romkan 继续提供现有体系 |
| 接口与分页 | 七个 MCP 工具返回结构化对象；联合结果顺序稳定，相邻页无同一 ID 重复 |
| 来源及语言 | 来源、快照和保留字段可定位；语言参数继续接受开放代码，保留 und |
| 运行资源独立 | 隔离原库与归档后，候选包中的 JSON、SQLite、verba、romkan 和配置足以完成上述调用 |
| 体积 | 在同一交付记录中列出数据库、原生数据、运行源码、配置和 Python 项目依赖的实际体积 |

不另行加入大批新语言数据做扩展实验，不检查翻译准确率或保义率。构建时保留记录和覆盖变化清单；功能验收使用有限场景，不在最后重新全表对照。

若一次验收暴露问题，如实登记结果与修复情况，按项目约定不循环重验；未得到确认的部分保持明确状态，不能仅因修了代码就写成“已全部通过”。

### 十、完成条件与体积口径

本轮完成的实质条件为：默认保留清单中的查询能力可用；源记录共有内容集中保存；公开 ID、关系和来源可追踪；运行包能脱离归档；构建和归档路径有说明；本阶段一次验收结果如实保存。

1–2 GiB 指默认安装后的运行资源及项目依赖合计，包含统一数据库、原生数据库和 JSON、必要第三方模块及词典、配置和说明；不包含归档、构建临时文件及系统 Python 安装。压缩下载包体积另外记录，不与安装体积混用。

若保留现有覆盖后仍超过 2 GiB，记录实际体积和主要来源即可。进一步的语言或词汇裁剪单列为可选策略，不能为了满足体积目标静默减少默认覆盖。

本轮不训练模型、不新增大型前端、不全面重写 MCP、不建立完整 Concept 网络、不自动合并跨来源姓名实体，也不清空原始归档。完成本轮后，再规划名称拉丁化与创作 skill 如何组合这些查询能力。
